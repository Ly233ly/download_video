# Tk 桌面程序首轮性能诊断与基线

日期：2026-07-29
阶段：诊断、复现、测量与排序；本报告没有修改运行时代码。

## 1. 结论先行

1. **当前安装版与工作区源码不是同一版本，这是目前最先要解决的验证障碍。** Windows 中实际安装的是 `1.4.3`，工作区是 `1.4.5`。安装版可见窗口创建中位数为 `795.1ms`，当前源码为 `488.7ms`；安装版约慢 `62.7%`。这个差值包含旧 UI 实现、冻结程序启动、导入和安全软件检查等因素，暂时不能全部归因于某一个函数。
2. **安装版 1.4.3 的“启动时一次创建全部页面、每次刷新处理隐藏页面”是已确认的 P1 问题。** 旧基线在 1000 条 IDM 压力数据下，强制刷新最差为 `197.6ms`，会明显跨过 100ms 感知门槛。当前源码已经改成首屏建页、后台分批预热、只投影当前页；但这些改动没有进入现在安装的软件。
3. **当前源码的周期刷新暂未发现超过 50ms 的证据。** 媒体场景刷新最大 `14.7ms`；1000 条 IDM 场景最大 `20.5ms`。因此不能把当前源码的普通周期刷新继续描述成 P1。
4. **当前源码仍有一次性切页尖峰。** 在关闭测试预热时，首次打开未创建页面为 `37–78ms`，其中视频号页约 `77–78ms`。它属于 P2：能感到一下“粘”，但不是持续卡死。
5. **没有发现后台线程直接操作 Tk 控件的已确认违规。** 当前后台任务通过 `Queue` 或变更监听把结果交给 Tk 主线程；FFmpeg、yt-dlp 和媒体处理位于线程池或外部进程。也没有发现无限增长的日志 Text、Treeview 追加或图片缓存。
6. **30 秒安装版空闲观测没有出现立即失控的内存增长。** RSS 在约 15 秒后稳定在 `65.2MB` 左右。但 30 秒不能证明两小时运行无泄漏，长期捕获场景仍需专门验证。

## 2. 项目运行流程

```text
程序入口 main.py
  ├─ 同步初始化 SQLite 数据库
  ├─ 创建 ProcessingService
  ├─ 创建 LocalApiServer
  │   ├─ 配对管理
  │   ├─ MediaCoordinator（2 个媒体工作线程）
  │   └─ 视频号捕获服务
  ├─ 启动本机 API 后台线程
  ├─ 启动 IDM/Eagle 任务处理后台线程
  └─ Tk 主线程创建 MainWindow 并进入 mainloop

Tk 主线程
  ├─ 输入、切页、布局、Canvas 与 Treeview 更新
  ├─ 读取轻量 SQLite 摘要和当前页数据
  ├─ 轮询后台 Queue
  └─ 通过 after 安排后续刷新

后台线程/外部进程
  ├─ Eagle 状态探测
  ├─ 更新检查与下载
  ├─ 视频号启停、证书预检、代理修复、预览读取
  ├─ 媒体下载与任务处理
  └─ FFmpeg / yt-dlp 子进程
```

主要代码证据：

- 入口与组件创建：`src/idm_eagle_bridge/main.py:42-88`
- 数据库同步初始化：`src/idm_eagle_bridge/database.py:208`
- 媒体线程池和启动恢复：`src/idm_eagle_bridge/media.py:209-228`
- API 服务线程：`src/idm_eagle_bridge/api_server.py:306-331`
- IDM/Eagle 处理线程：`src/idm_eagle_bridge/service.py:18-34`
- Tk 主窗口和队列：`src/idm_eagle_bridge/ui.py:2718-2818`

## 3. Tk 主线程职责与耗时边界

### 已确认在 Tk 主线程执行

| 位置 | 触发方式 | 工作 | 测量/判断 |
| --- | --- | --- | --- |
| `ui.py:4807-4983 MainWindow.refresh` | 750–4000ms 周期刷新、页面变化、后台变更事件 | 轻量状态、SQLite 摘要、当前页面投影 | 当前源码最大 `20.5ms`；安装版旧逻辑最差 `197.6ms` |
| `ui.py:2920-2996 _ensure_page/_show_page` | 第一次切换到未创建页面 | 创建该页面的 Tk 控件并布局 | 当前源码首次 `37–78ms`；后台预热通常会提前完成 |
| `ui.py:4912-4964 IDM 行投影` | IDM 修订号变化且 IDM 页可见 | 读取最多 500 条，显示当前页 80 条，测量文字宽度 | cProfile 中 240 次文字测量累计约 `84ms`，但分析器本身有明显开销；无分析器的整轮刷新最大 `20.5ms` |
| `ui.py:5670-5685 _plan_thumbnail` | 当前页卡片需要缩略图 | Tk `PhotoImage` 解码小尺寸 PNG | cProfile 中 12 张约 `8ms`；预览由后台 FFmpeg 限制为 240px，缓存上限 64 |
| `ui.py:6539-6603 export_diagnostics` | 用户导出诊断 | 查询 500 条任务和 200 条媒体记录、JSON 格式化、写盘 | 未做 UI 端单独实测；低频同步 I/O 风险 |
| `ui.py:6616-6638 clear_*_history` | 用户确认清理 | 同步 SQLite 删除，再刷新 | 10000 条终态记录清理 `45.7ms`；低频但接近一帧 50ms 门槛 |
| `ui.py:6640-6652 copy_pairing_code` | 点击复制配对码 | 剪贴板写入并调用 `root.update()` | 低频；存在事件循环重入风险，没有当前卡顿证据 |

## 4. 线程、进程、Queue 与 Tk 安全

| 执行单元 | 创建位置 | 工作 | 回到 Tk 的方式 | 当前结论 |
| --- | --- | --- | --- | --- |
| 本机 API 线程 | `api_server.py:306-331` | HTTP 服务 | 业务状态由数据库/服务读取 | 正常 |
| 任务处理线程 | `service.py:18-34` | IDM/Eagle 队列处理 | 数据库状态 + 唤醒 | 正常 |
| 媒体线程池（2） | `media.py:218-228` | 下载、合并、验证、预览 | 变更监听向 `media_change_events` 放消息 | 正常 |
| FFmpeg/yt-dlp 进程 | `media.py` 多处 `subprocess` | CPU/I/O 重任务 | 工作线程等待，Tk 不等待 | 正常 |
| 视频号代理线程 | `wechat_channels_proxy.py:622-639` | 本地代理监听 | 捕获服务状态/候选注册表 | 需做真实捕获压力测量 |
| 视频号每连接线程 | `wechat_channels_proxy.py:509` | 代理请求和响应处理 | 不直接操作 Tk | 线程数量与 GIL 竞争尚未实测 |
| Eagle 探测线程 | `ui.py:966-982` | 可用性探测 | `_AsyncProbe._results` Queue | 正常 |
| 更新线程 | `ui.py:4660-4774` | 检查、下载 | `update_events` Queue | 正常 |
| 视频号操作线程 | `ui.py:5343-5606` | 预览、预检、启停、代理修复 | 两个视频号 Queue | 正常 |

已找到的 UI 队列：

- `_AsyncProbe._results`：Eagle 探测结果。
- `media_change_events`：媒体状态变更，250ms 合并消费。
- `update_events`：更新检查、下载进度和结果。
- `wechat_preview_events`：预览图片字节。
- `wechat_operation_results`：证书预检、捕获启停和代理修复结果。

**已确认事实：** 当前后台 worker 函数只把普通数据或字节写入 Queue，没有直接调用 `Label.config`、`Treeview.insert`、`PhotoImage`、`StringVar.set` 或 `messagebox`。Tk 更新仍在主线程完成。

## 5. 长期 after 任务与生命周期

| 任务 | 周期 | 生命周期与取消 | 判断 |
| --- | ---: | --- | --- |
| 媒体变更 Queue | 250ms | 保存 `media_change_after_id`，退出时取消 | 正常；会合并队列内全部变更 |
| 托盘控制信号 | 250ms | 保存 `control_after_id`，退出时取消 | 正常 |
| 页面刷新 | 可见 750–4000ms；隐藏 30s；拖窗时 240ms 延后 | 保存 `refresh_after_id`，每轮先取消旧任务，退出时取消 | 正常 |
| 页面预热 | 启动 900ms 后；每页间隔 450ms；拖窗时 500ms 延后 | 保存 `prewarm_after_id`，队列清空后停止，退出时取消 | 正常 |
| 更新事件 | 仅更新活动期间 150ms | 保存 `update_poll_after_id`，活动结束停止，退出时取消 | 正常 |
| 自动更新 | 启动 10s 后一次 | 保存 `auto_update_after_id`，退出时取消 | 正常 |
| 窗口布局 | Configure 后 90ms，停止拖动后 180ms | 保存 ID，重复事件取消前一项，退出时取消 | 正常的防抖 |
| 视频号操作结果 | 操作期间 200ms | 没有保存 after ID；由 `wechat_operation_busy` 控制并在结果到达后停止 | 没有泄漏证据，但生命周期可更明确，P4 |
| 复制反馈 | 1500ms 一次 | 保存 ID，退出时取消 | 正常 |

其余 `after_idle` 主要用于文字换行、圆角控件重绘、Treeview 列宽、滚动区域、预览比例和响应式布局。多数保存待处理 ID 或尺寸/状态签名，从而把同一事件风暴合并到一次空闲绘制。

当前源码的测试夹具在连续刷新后报告 `pending_tk_callbacks = 0`。这个数字只证明测试中启用的一次性回调能够排空；夹具会关闭长期周期任务，因此不能拿它证明真实窗口完全没有 after 任务。

退出时 `ui.py:6663-6701` 会取消刷新、页面刷新、预热、托盘、布局、更新、复制反馈和媒体变更计时器，并移除媒体监听。

## 6. 高频刷新、控件、Canvas、Treeview、图片和日志

### 当前源码已确认的保护

- `refresh` 只重建当前可见页，隐藏页不再做列表投影。
- 页面延迟创建，启动只建媒体页；随后分批预热。
- 媒体和 IDM 使用修订号，未变化时不重建列表。
- 媒体、视频号列表有分页；当前候选注册表只向 UI 暴露当前项：`wechat_channels.py:434-437`。
- 视频号内部预览缓存上限 50：`wechat_channels.py:536-539,907-911`。
- 媒体 Tk 缩略图缓存上限 64：`ui.py:5670-5685`。
- FFmpeg 在后台生成 `scale=240:-2` 的预览：`media.py:1568-1598`。
- 没有发现无限追加的 Tk `Text` 日志框。
- Treeview 通过同步现有行的方式投影，不是永久追加。

### 仍需关注

- 圆角按钮、导航、滚动条和进度条中的部分 Canvas 会在状态签名变化时重画全部对象。它们已做 `after_idle` 合并；当前没有 Canvas 项持续增长证据，暂列 P4。
- 第一次建视频号页、设置页仍会一次创建较多控件，形成 37–78ms 尖峰。
- IDM 当前页 80 行会做多次字体宽度测量；数据修订频繁时可能产生可见尖峰，需要事件级监控后再决定是否缓存。
- 视频号代理会为连接创建线程并缓存/解压有限大小的响应。真实微信预加载时可能与 Tk 争抢 GIL，但当前没有实测证据，不能写成已确认瓶颈。

## 7. 可复现步骤

### 场景 A：验证安装版与源码不一致

1. 打开当前安装的“下载中转站”。
2. 查看标题栏或“设置 > 更新”中的版本，应为 `1.4.3`。
3. 对照工作区 `pyproject.toml` / 应用常量的 `1.4.5`。
4. 成功标志：确认当前手感测试并不是在运行这份工作区源码。

### 场景 B：复现安装版旧的全局刷新卡顿

1. 使用约 1000 条 IDM 历史/压力数据启动安装版或 `v1.4.3` 源码。
2. 打开任意页面，让后台刷新继续运行。
3. 同时拖动窗口、滚动列表或连续切页。
4. 记录刷新回调超过 50/100ms 的次数。
5. 参考旧基线：强制刷新最差 `197.6ms`，属于明显可感知停顿。

### 场景 C：复现当前源码首次切页尖峰

1. 以当前源码启动，并暂时关闭测试夹具中的页面预热。
2. 启动后立即依次进入“视频号”“IDM 导入”“设置”“诊断”。
3. 首次进入记录 `37–78ms`；第二次进入记录 `8–20ms` 左右。
4. 若实际启动后等待约 3 秒再切页，预热应显著降低首次尖峰。

### 场景 D：拖动、缩放和滚轮事件风暴

1. 打开有任务卡片和详情的媒体页。
2. 连续拖动窗口边缘 10 秒，再快速来回改变宽度。
3. 同时用鼠标滚轮/触控板滚动 120 次。
4. 检查文字残影、重复滚动条、CPU 峰值、Tk 事件延迟和 after 积压。
5. 当前确定性基线：60 步缩放总计 `80–107ms`；120 次滚轮路由 `1.26–1.28ms`。这不是 DWM 帧率，只是回调总耗时。

### 场景 E：视频号真实捕获压力

1. 开始捕获后，在微信视频号连续浏览 10 分钟，让页面发生预加载。
2. 每 1 秒记录 UI 心跳延迟、CPU、RSS、私有内存、线程数、候选保留数和 Queue 长度。
3. 同时拖动窗口和切页。
4. 抓取一次 30–60 秒调用栈采样，判断代理线程是否与 Tk 主线程争抢 GIL。
5. 这一场景本轮没有真实执行，因此只列为待验证。

### 场景 F：长期运行

1. 分别在“空闲”“持续下载”“视频号持续捕获”三种状态运行 2 小时。
2. 每 60 秒记录 CPU、RSS、私有内存、线程数、Tk after 数和各 Queue 长度。
3. 每 10 分钟执行一次切页、滚动和窗口拖动。
4. 判断是否出现单调增长、回调积压或页面销毁后继续更新。

## 10. 下一轮基线方案

在动下一行性能代码前，建议按这个顺序：

1. **构建当前源码的可回退候选包。** 使用同一数据目录的副本，不直接覆盖现有安装版。
2. **给 Tk 主线程加轻量“心跳”和回调计时。** 记录超过 50ms、100ms、500ms 的回调名称、页面和当时队列长度；默认关闭详细日志，避免测量本身制造卡顿。
3. **同一脚本测三组版本。** 当前 1.4.3、当前源码、1.4.5 冻结候选包；每组至少 5 次冷启动和 10 次热启动。
4. **采集真实业务矩阵。**
   - 空闲；
   - 1000 / 10000 条 IDM 历史；
   - 12 个媒体卡片 + 活动下载；
   - 视频号持续预加载；
   - 更新下载；
   - 诊断导出和历史清理。
5. **测真实交互。** 首次/再次切页、窗口连续拖动 10 秒、120 次滚轮、按钮点击到反馈、退出。
6. **做两小时稳定性观测。** 每 60 秒记录 CPU、RSS、私有内存、线程、after 数和 Queue 长度；出现单调增长再定位对象归属。
7. **视频号场景单独做采样。** 使用 Windows 性能记录或 Python 采样器抓取 30–60 秒栈，确认是 Tk、SQLite、代理线程、杀毒扫描还是 DWM 合成占用。

建议的体验门槛：

- 常规主线程回调 P95 < 16ms，最大 < 50ms；
- 高频刷新不得出现 >100ms；
- 已预热页面切换 P95 < 30ms；
- 首次页面切换最大 < 50ms；
- 拖动期间不执行强制列表刷新；
- 两小时稳定状态下，RSS、线程、after 和 Queue 不持续单调增长；
- 关闭窗口后无 TclError，后台线程按预期退出。
